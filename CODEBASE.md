## 1. PROJECT OVERVIEW

### Tech Stack
| Layer | Technology |
|-------|-----------|
| Framework | .NET 10, Blazor Server |
| UI Library | MudBlazor |
| Database | MariaDB (MySQL protocol) |
| ORM | EF Core (Entity Framework Core) |
| OCR/AI | Azure Document Intelligence (Azure DI) |
| Authentication | Custom session-based via `IAuthService` + `ErpUser` table |
| Deployment | Docker container |

### Project Purpose
NordicBeesERP is a **custom ERP system for MB Lakštena** — a Lithuanian beekeeping business that produces and sells beekeeping products (honey, beeswax, pollen, etc.). It manages:
- Sales invoicing (B2B/B2C)
- Payments and bank reconciliation
- Warehouse/inventory management with lot tracking
- Production batch management with traceability
- Supplier (beekeeper) management
- Expense invoice processing with OCR
- Credit notes

### Authentication
- Custom session-based auth via `AuthService` + `ErpUsers` table
- `Users` table exists but is **empty and unused** for authentication
- ERP users stored in `erp_users` table with role-based access control
- Auth state managed by `BlazorAuthStateProvider`

### Deployment
- Containerized via Docker
- Environment-specific config: `appsettings.Development.json`, `appsettings.Production.json`

## 6. KNOWN ISSUES

### 6.1 Dead Columns in `invoices` Table

The following columns in the `invoices` table are **dead columns** — they exist in the schema but are **not used by the application** and should be removed:

| Column | Issue |
|--------|-------|
| `payment_term_id` | References non-existent `payment_terms` table; should use `business_partners.payment_term_days` instead |
| `payment_term_id1` | Same as above (naming inconsistency from migration) |
| `created_by` | References `users.id` but `users` table is empty; auth uses `erp_users` |
| `creator_id` | Duplicate of `created_by` |
| `delivery_id` | References `deliveries.id` but sales invoices are unrelated to honey deliveries |

**Recommendation:** These columns should be removed in a cleanup migration after verifying no active code depends on them.

---

### 6.2 Duplicate Columns in `bank_imports` Table

The `bank_imports` table has **duplicate columns** with different names — likely from separate migrations:

| Column A | Column B | Issue |
|----------|----------|-------|
| `file_name` | *(no direct duplicate, but inconsistent)* | Only `file_name` exists |
| `row_count` | `total_rows` | Both represent same concept |
| `total_debits` | *(exists)* | OK |
| `total_credits` | *(exists)* | OK |
| `transaction_count` | *(exists)* | OK |
| `status` | *(exists)* | OK |

**Recommendation:** Audit `BankImport` model and related service to ensure consistent field usage. Remove any redundant columns if they serve no purpose.

---

### 6.3 Empty `users` Table with Unused FK

The `users` table:
- Has **no data** (completely empty)
- Has `invoices.created_by` referencing `users.id` — but this FK is **never populated**
- **Real authentication** uses `erp_users` table instead

**Impact:**
- `invoices.created_by` FK is dangling (references non-existent users)
- `AuditLog. UserId` may also reference non-existent users

**Recommendation:** Either:
1. Migrate data from `erp_users` to `users` and update all FK references, OR
2. Change FK references to point to `erp_users.id` and remove the `users` table

---

### 6.4 Missing Foreign Key Constraints

Several FK references are **missing** from the database schema, causing potential data integrity issues:

| Table | Column | References | Status |
|-------|--------|------------|--------|
| `expense_invoices` | `supplier_id` | `business_partners.id` | ❌ Missing FK |

### 6.5 Inconsistent CASCADE DELETE Strategy

The project has **no consistent CASCADE DELETE policy**:
- Some relationships use **soft delete** (`is_active` flags)
- Some use **ON DELETE SET NULL**
- Some use **ON DELETE CASCADE** (implicit, not enforced)
- Financial records (invoices, payments) should **never be physically deleted**

**Current approach:**
- Expense invoices: soft delete via status (`REJECTED`, `CANCELLED`)
- Customers/Suppliers: soft delete via `is_active` flag
- Audit logs: always preserved
- Stock movements: always preserved for traceability

**Recommendation:** Document a clear DELETE strategy:
1. **Financial records** (invoices, payments, credit notes) — NO physical delete, use status/cancellation
2. **Audit logs** — NEVER delete, ever
3. **Reference data** (categories, units) — soft delete via `is_active`
4. **Temporary data** (OCR queue, bank import rows) — can be cascade deleted
